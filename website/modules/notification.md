# 通知管理

通知管理用于配置作业成功 / 失败与调度器异常的消息推送，并保留发送历史。底层通过 **PushPlus** 投递，不需要自己维护 SMTP 或机器人。

![通知管理](/images/notification.png)

## 1. 页面构成

| 区域 | 说明 |
| --- | --- |
| 工具栏 | 通知配置、发送测试通知、清空 |
| 筛选区 | 通知状态、触发来源 |
| 列表 | 标题、来源、状态、发送时间、耗时、创建时间 |
| 操作 | 查看详情、删除 |

## 2. 通知配置

点击「通知配置」打开对话框，分为基础配置、渠道参数、高级配置与通知策略。

### 2.1 基础配置

| 配置项 | 说明 |
| --- | --- |
| 服务启用状态 | 总开关，关闭后不发送任何通知 |
| Token | PushPlus 个人 Token，必填 |
| 推送渠道 | 微信公众号、企业微信、Webhook、邮件、短信、语音、浏览器扩展、App |
| 消息模板 | HTML / Markdown / TXT / JSON |

### 2.2 渠道参数

| 配置项 | 适用渠道 | 说明 |
| --- | --- | --- |
| 业务主题（Topic） | 全部 | 群组编码，填写后发给群组；不填则发给个人 |
| 渠道配置（Option） | webhook、cp、mail | webhook 填 Webhook 编码；cp 填企业微信应用编码；mail 可选自定义邮件渠道 |
| 接收人（To） | wechat、cp | 好友令牌或企业微信用户 id，多人用逗号分隔 |

`Topic` 与 `To` 不建议同时使用，`Topic` 优先级更高。选择 webhook 等渠道时，`Option` 为空会阻止保存。

### 2.3 高级配置

- **回调地址**：接收 PushPlus 的发送结果回调，选填；
- **有效期时间戳**：毫秒时间戳，服务器时间超过该值则不发送。

### 2.4 通知策略

| 策略 | 默认值 |
| --- | --- |
| 作业执行成功 | 关闭 |
| 作业执行失败 | 开启 |
| 调度器系统异常 | 开启 |

## 3. 消息模板

v2.7.0 起模板改为卡片式选择器，选中后在下方实时预览；标题栏保留「推送预览」入口，预览以悬停浮层展示。

| 模板 | 适用场景 |
| --- | --- |
| HTML | 微信内阅读，带状态色块与表格 |
| Markdown | 技术人员阅读，结构清晰 |
| TXT | 短信、语音等纯文本渠道 |
| JSON | 对接下游系统或自动化流程 |

JSON 模板输出示例：

```json
{
  "eventType": "jobExecution",
  "jobName": "order-sync",
  "jobGroup": "DEFAULT",
  "status": "failed",
  "statusText": "失败",
  "executionTime": "2026-11-17 10:00:00"
}
```

测试通知也会按当前模板生成内容，可直接验证模板效果。读取旧配置时，缺失的模板或策略字段会补默认值。

配置步骤与 PushPlus 注册见 [通知配置](/guide/notification)。

## 4. 通知历史

列表展示：

| 字段 | 说明 |
| --- | --- |
| 通知标题 | 通常包含作业名与状态 |
| 触发来源 | 作业名或「调度器」 |
| 状态 | 待发送 / 发送成功 / 发送失败 |
| 发送时间 | 实际提交时间 |
| 耗时 | 发送耗时（毫秒） |
| 创建时间 | 记录生成时间 |

支持按状态筛选、按来源搜索、查看详情、单条删除与批量清空。详情包含完整内容、错误信息与时间信息。

## 5. 测试通知

点击「发送测试通知」验证配置：

- 成功：提示发送成功；
- 失败：提示失败原因。

测试通知**不会写入通知历史**，失败时请查看应用日志。常见原因：

1. Token 无效；
2. 服务器无法访问 PushPlus；
3. 当前渠道缺少必填的 `Option`；
4. 模板与渠道格式不兼容。

## 6. 能力边界

| 想实现 | 是否支持 |
| --- | --- |
| 为单个作业单独配接收人 | 不支持，通知为系统级配置 |
| 为单个作业单独选模板 | 不支持，模板全局生效 |
| 作业超时通知 | 不支持，只有成功 / 失败 / 调度器异常 |
| 作业跳过通知 | 不发送，只写「已跳过」日志 |
| 通知历史导出 | 不支持 |

如果需要按作业分流，需要在宿主应用中自行实现通知逻辑。

## 7. 建议

- 保持失败与调度器异常通知开启；
- 成功通知只在关键链路开启，避免噪声；
- 每次修改配置后发一条测试通知；
- 定期清理历史，或结合数据库备份保留。
