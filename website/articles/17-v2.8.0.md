# v2.8.0：手动中断运行中的作业

v2.8.0 发布于 2026-11-24。这一版的主线只有一句话：**让跑着的作业能被叫停。**

先看三个实际场景：

| 场景 | v2.8.0 之前 | v2.8.0 |
| ---- | ----------- | ------ |
| 作业配错了参数，正在跑一个 40 分钟的全量同步 | 只能等它跑完，或者停调度器 | 日志页点「中断」，立刻发出取消信号 |
| 同一作业并发跑了 3 个实例，只有 1 个要停 | 无法区分 | 按 `fireInstanceId` 精确中断目标实例 |
| 手动停掉的作业第二天自己又跑了一遍 | 被当成异常中断补偿重跑 | 手动中断不进入自动补偿 |

除了中断，这一版还统一了通知推送的卡片样式、给通知详情加了多格式渲染，并把 Quartz 从 `3.15.1` 升到了 `3.22.10`。

::: tip v2.8.1 补丁（2026-11-26）
修复 MySQL 扩展包在 net8.0 / net10.0 下依赖解析到低版本 EF Core 导致的启动报错；同时修掉 .NET 8 / .NET 10 目标下的依赖安全漏洞（EF Core、Npgsql、JwtBearer、Pomelo、MySqlConnector）。无公共 API 变更，无数据库结构变更。
:::

## 1. 为什么以前“停不下来”

三个事实叠在一起，导致以前没有“中断”这个能力：

1. **线程不能被强杀**。.NET Core 起 `Thread.Abort` 直接抛异常，运行时层面不存在“安全地结束一个正在跑的线程”；
2. **Quartz 的 `Interrupt` 是请求，不是命令**。它只是把该执行的 `CancellationToken` 置为已取消，作业必须自己观察令牌才会退出；
3. **日志是在执行结束后写的**。没有“运行中”的记录，页面上根本没有可以操作的对象。

v2.7.0 解决了第 3 点（执行开始即写 `Running` 日志 + 心跳续期），v2.8.0 才有可能在第 1、2 点的约束下做出真正可用的中断。

## 2. 一次中断的完整链路

```text
点击「中断」
  └─ 校验日志：存在 → 状态为运行中 → 属于当前节点（InstanceId / BootId 匹配）→ 调度器可用
       └─ 定位执行实例：按 JobKey 过滤，取触发时间最接近该日志 StartTime 的那一条
            └─ 先把日志标记为「中断」，补偿状态置为「已跳过」
                 └─ 再发 Interrupt 信号：优先 fireInstanceId，失败回退 JobKey
                      └─ 作业观察到取消 → 抛 OperationCanceledException → 监听器保留中断状态收尾
```

四个刻意的设计选择：

| 行为 | 原因 |
| ---- | ---- |
| **先标记、后发信号** | 中断会让作业立刻抛取消异常。如果监听器抢先收尾，会把日志改写成「失败」；先标记后，监听器看到「已标记中断 + 令牌已取消」就会保留中断状态 |
| **补偿状态置为「已跳过」** | 手动中断不应该被启动期自动补偿再跑一遍，否则“我手动停掉的作业，第二天自己跑了” |
| **定位到具体执行实例** | 同一作业允许并发时，只中断目标实例，不影响其它在跑的实例 |
| **校验节点归属** | 当前是内存 JobStore（单进程）。进程重启后残留的 `Running` 记录在本进程内并不存在对应执行，必须直接拒绝，而不是误标为中断 |

### 2.1 实例怎么定位

日志里有 `JobName` + `JobGroup` + `StartTime`，调度器里能拿到 `GetCurrentlyExecutingJobs()`。定位规则：

1. 先按 `JobKey` 过滤出该作业当前所有执行；
2. 按 `|FireTime - 日志.StartTime|` 排序，取差值最小的一条；
3. 用它的 `FireInstanceId` 调 `Interrupt`；
4. 精确中断返回 `false`（例如刚开始/刚结束的临界情况）时，回退到 `Interrupt(JobKey)`。

这样并发场景下不会“一键停掉整个作业的所有实例”。

### 2.2 错误码

`POST /api/quartz/InterruptJob` 沿用统一响应结构 `{ success, message, data, errorCode }`：

| 错误码 | 含义 |
| --- | --- |
| `LOG_NOT_FOUND` | 日志不存在 |
| `LOG_NOT_RUNNING` | 不是运行中的记录 |
| `LOG_NOT_ON_THIS_NODE` | 执行不在当前节点，或已随进程重启结束 |
| `SCHEDULER_NOT_RUNNING` | 调度器已停止 |
| `EXECUTION_NOT_FOUND` | 没找到正在执行的实例（可能刚结束） |
| `EXECUTION_FINISHED` | 标记时执行已结束 |

## 3. 状态与展示：一个状态，两种来源

中断有两个来源：**进程崩溃 / 停机超时**（v2.7.0 已有）和**用户手动点击**（v2.8.0 新增）。它们共用同一个状态值 `Interrupted`，不新增枚举，也不改表结构。

区分方式是在跳过原因前加固定前缀：

```csharp
public const string ManualInterruptPrefix = "【手动中断】";
// 实际写入：SkipReason = "【手动中断】用户手动中断作业"
```

展示层的约定：

| 位置 | 表现 |
| --- | --- |
| 日志列表状态列 | 统一显示「中断」 |
| 状态悬浮提示 | 前缀命中显示「手动中断」，否则显示「异常中断」 |
| 详情页「恢复信息」 | 新增「中断方式」一行 |
| 跳过原因 | 展示时裁掉前缀，只显示「用户手动中断作业」 |

> 前缀只用于展示，**不能作为查询或统计条件**。需要统计时应基于 `CompensationStatus` 或新增字段，而不是字符串匹配。

## 4. 谁来真正停下：作业必须配合

平台只能“请求”作业停下。不同作业类型点击中断后的实际效果：

| 作业类型 | 效果 |
| --- | --- |
| API 作业（界面配置） | 平台内置 `ApiJob` 已把令牌链进 HTTP 请求，请求立即取消，**无需写代码** |
| 正在等待重试的包装器 | 等待中的 `Task.Delay` 已接令牌，立即结束，**无需写代码** |
| 自定义 DLL 作业，接了令牌 | 在下一个等待点 / 检查点退出，**推荐做法** |
| 自定义 DLL 作业，没接令牌 | 令牌只是被置位，作业继续跑完，最终日志被真实结果覆盖 |

最小改造只有三个动作：

```csharp
public async Task Execute(IJobExecutionContext context)
{
    var token = context.CancellationToken;                 // ① 用 Quartz 注入的令牌

    await Task.Delay(TimeSpan.FromSeconds(30), token);     // ② 所有等待/IO 传令牌
    using var response = await _httpClient.GetAsync(url, token);

    foreach (var item in items)                            // ③ 长循环设检查点
    {
        token.ThrowIfCancellationRequested();
        await ProcessAsync(item, token);
    }
}
```

三个必须避免的坑：

1. **不要吞掉取消异常**：`catch (OperationCanceledException) { }` 会让作业“正常返回”，日志被改成成功；
2. **不要把取消当业务失败**：取消是预期行为，不要写失败结果、不要触发重试；
3. **不要在 `catch` / `finally` 里继续长时间工作**：收尾耗时过长，会让中断看起来没生效。

完整改造示例（含 `Thread.Sleep`、同步 SDK 等替换写法）见 [手动中断运行中的作业](/guide/manual-interrupt)。

> 真正需要“无论如何必须停”的场景（第三方库内部死循环），只能走进程隔离：把这类作业放到独立进程 / 容器，中断时直接结束进程。Quartz 层面没有这个能力。

## 5. 通知推送：一张卡片走到底

v2.8.0 之前，作业执行通知、调度器异常通知、测试通知各写一套 HTML，样式和字段命名都不统一。现在收敛到一个构建器：

```csharp
private static string BuildHtmlCard(string title, string subtitle, string accent,
    params (string Label, string Value, string? Color)[] rows)
```

- `BuildHtmlRows(...)` 负责“标签 : 值”的行，支持按状态着色；
- 所有插入内容都过 `Html()`（`WebUtility.HtmlEncode`）转义，作业名、消息、堆栈里的 `<`、`&` 不会破坏结构，也不会引入注入；
- 作业执行、调度器异常、测试通知三条链路共用同一套结构，与前端「推送预览」的外观一致；
- 耗时统一走 `DurationFormatter.Format(ms)`：`850 毫秒` / `1.28 秒` / `5.2 分钟` / `2.56 小时`，推送和邮件里不再出现一长串毫秒数。

## 6. 通知详情：按内容推断格式再渲染

历史通知记录**没有保存模板类型**，所以详情页不能靠字段判断该用哪种方式展示。做法是按内容特征推断：

```ts
detectContentFormat(content) // → 'html' | 'markdown' | 'json' | 'txt'
```

判定顺序：

| 顺序 | 规则 | 结果 |
| --- | --- | --- |
| 1 | 以 `{` / `[` 开头、`}` / `]` 结尾，且能被 `JSON.parse` 解析 | `json` |
| 2 | 命中 HTML 标签特征（`div`、`table`、`tr`、`p`、`br` 等） | `html` |
| 3 | 命中 Markdown 特征（标题、表格、代码块） | `markdown` |
| 4 | 其它 | `txt` |

JSON 之所以要求“能被解析”，是为了避免把以 `{` 开头的普通文本误判成 JSON。

渲染方式：

- **HTML**：直接渲染为富文本卡片；
- **Markdown**：走一个轻量渲染器，覆盖后端模板会产出的语法（标题、表格、分隔线、代码块、有序 / 无序列表、引用、行内代码 / 粗体 / 斜体 / 删除线 / 链接），为了一个详情面板不值得引入完整 Markdown 依赖；
- **JSON**：解析成功则缩进 2 空格输出，失败原样展示；
- **TXT**：直接展示。

HTML / Markdown / TXT 三种格式支持「渲染 / 源码」切换，方便排查模板问题和推送内容差异；JSON 不提供切换（源码即渲染结果）。一键复制拿到的始终是**原始内容**，不是渲染后的 DOM。

## 7. 顺手修掉的两个问题

1. **日志文本含花括号导致异常**：日志消息里带 `{}` 时会被当成模板占位符解析而抛错。现在统一对日志文本做转义，并补全了部分缺失的操作名（列表里的“操作”列不再出现空白）。
2. **操作列图标不统一**：中断、详情、重新执行统一为字体图标，尺寸和间距一致，避免不同行之间跳动。

## 8. 依赖升级：Quartz 3.15.1 → 3.22.10

Quartz 这次跨了 7 个次版本，对本项目有用的变更主要是：

- **`CronTriggerImpl` 克隆共享 `JobDataMap`**：在 `RAMJobStore` 下，克隆出的 trigger 与源 trigger 共用同一个 `JobDataMap`，修改其中一个会污染存储中的另一个。项目用内存 JobStore + Cron 触发，这个缺陷会直接影响 `UpdateJob` 之后的行为，升级即可修复；
- **`JobDataMap.Put(...)` 标记过时**：库内部改用索引器写法（`map["key"] = value`），行为不变，使用方无需改动；
- 无公共 API 变更，无数据库 schema 变更。

::: tip 升级注意
`3.22.x` 的 `CronTriggerImpl` 行为与旧版一致，已存在的 Cron 表达式和历史触发器数据不需要迁移。
:::

## 9. 升级与兼容性

| 项 | 说明 |
| --- | --- |
| 数据库结构 | **无变更**，不需要执行迁移 |
| 公共 API | 只新增 `InterruptRunningJobAsync` 与 `POST /api/quartz/InterruptJob`，无破坏性改动 |
| 前端资源 | 随包内嵌，替换 DLL 后浏览器强制刷新即可 |
| 行为变化 | 手动中断的记录 `CompensationStatus` 为 `已跳过`，启动时不会自动补跑 |
| 作业改造 | 只有“希望被中断”的自定义 DLL 作业需要接 `context.CancellationToken`，不改造仍可正常运行 |

升级后建议做一件事：挑一个耗时最长、最不幂等的作业，实际点一次「中断」，确认它在预期时间内退出。如果没退出，说明作业代码里没有观察令牌——这时中断只会被记录，不会真正停止。

## 11. 小结

v2.8.0 解决的是一个很具体的运维痛点：**配错的作业正在跑，能不能立刻停掉。**

- 能停 → 日志页一键中断，按实例精确生效；
- 停得住 → 状态不会被监听器改写成失败或成功，补偿也不会误触发；
- 停不下来时 → 页面明确告诉你原因（错误码），而不是“点了没反应”；
- 停完还能再跑 → 「重新执行」把它变成「已补偿重跑」，来源链路完整。

前提是作业代码愿意配合。协作式取消不是限制，而是 .NET 里唯一安全的选择。
