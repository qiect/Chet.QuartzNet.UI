# 🚀 Chet.QuartzNet.UI v2.6.0 发布：作业依赖、批量操作、日志自动清理、五种存储迁移，轻量但不简陋！

又到了版本更新时间！这次 v2.6.0 没有堆砌重型功能，而是围绕「简单配置、上手就用」继续打磨：**作业依赖（工作流）**、**批量暂停 / 恢复 / 启用 / 禁用**、**日志自动清理**、**五种存储之间的数据迁移** 四件实事一次到位。

---

## 🧭 一、先说定位：轻量工具，不做重

有朋友问要不要加 RBAC 权限、操作审计、审批流这一套。答案是：**不加**。

Chet.QuartzNet.UI 的定位一直很明确 —— 一个轻量的定时任务可视化管理工具：

- 一个 NuGet 包，`AddQuartzUI()` 就能跑起来
- 文件存储零依赖，数据库存储按需切换
- 配置项能少就少，打开就能用

所以 v2.6.0 的取舍是：**把日常运维最常用的能力做扎实，而不是把系统做重。**

## 🔗 二、作业依赖：轻量版工作流

「A 跑完再跑 B」是定时任务里最常见的诉求。v2.6.0 支持给作业配置**前置依赖作业**，但没有做复杂的 DAG 编辑器和自动触发链路，而是采用最直观的 **前置校验模式**：

### 执行规则

1. 作业被触发时，先检查所有前置依赖作业
2. 逐个查看依赖作业**最近一次执行**的结果
3. 全部成功 → 正常执行本作业
4. 有任意一个未执行或执行失败 → **本次直接跳过**，不执行作业本体

简单说：**依赖不满足，这次就不跑**，等下一次触发再判断。

### 配置方式

在作业编辑对话框里新增「前置依赖」多选框，按 `分组 / 作业名` 选择依赖作业，支持多选、搜索、一键清空。

依赖关系以 JSON 存储在作业表中，文件存储和数据库存储都支持；数据迁移时也会一并复制，不会丢配置。

### 跳过会留下证据

依赖不满足时不会静默跳过，而是写入一条「**已跳过**」状态日志，消息里会明确告诉你原因，例如：

```
前置依赖未满足，本次执行已跳过：
demo.job-a 最近一次执行状态为 Failed
```

或者依赖作业从来没跑过：

```
前置依赖未满足，本次执行已跳过：
demo.job-a 尚未执行
```

日志管理页已经新增「已跳过」状态的颜色标识与筛选条件，一眼就能定位被依赖卡住的作业。

### 保存时就拦住错误配置

依赖配错比不配更危险，所以保存时会做三重校验：

| 校验项 | 提示 |
|--------|------|
| 依赖自己 | 作业不能依赖自身 |
| 依赖不存在的作业 | 依赖作业不存在: 分组.名称 |
| 形成循环依赖（A→B→A） | 存在循环依赖，请检查前置依赖配置 |

### 一个小细节：手动触发不走依赖校验

「立即执行」是人工干预手段，和现有的手动触发忽略暂停状态保持一致 —— **手动触发会绕过依赖校验**，方便你在依赖异常时手动补跑。

## 🎛️ 三、批量操作：一次选中，一起处理

作业多了以后，一个个点开关、点暂停太折磨人。v2.6.0 的作业列表支持多选 + 批量操作：

- ✅ **批量暂停** —— 临时停掉一批作业
- ✅ **批量恢复** —— 一次性恢复运行
- ✅ **批量启用** —— 把禁用状态的作业重新纳入调度
- ✅ **批量禁用** —— 不删除配置，只是退出调度

操作入口在工具栏的「批量操作」下拉菜单里，未选中作业时按钮自动禁用；执行前有二次确认，避免误伤。执行完成后会返回结果统计：

```
批量暂停完成，成功 9 个，失败 0 个
```

这里有个容易踩的坑也处理了：**批量启用会保留作业原来的暂停状态** —— 原来处于「暂停」的作业，启用后仍然是暂停状态，不会因为一次批量启用就偷偷跑起来。

## 🧹 四、日志自动清理：再也不用担心日志表撑爆

日志越攒越多，查询越来越慢，是定时任务系统绕不开的问题。v2.6.0 在系统配置页新增「日志自动清理」：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| 日志保留天数 | 30 | 超过天数的日志自动清理，0 = 不按天数清理 |
| 日志最大条数 | 0 | 超过条数时清理最旧的日志，0 = 不限制 |
| 清理间隔（小时） | 6 | 后台清理任务的执行周期 |

后台服务启动 60 秒后开始工作，之后按配置的间隔循环清理，同时支持两种策略：

- 按**保留天数**清理过期日志
- 按**最大条数**保留最新的日志，清理溢出部分

清理完成后会输出日志，例如：

```
[作业日志自动清理] 清理完成，共清理 153 条日志，下次清理间隔 6 小时
```

不需要手动点按钮，也不占用前台请求，配置一次就长期生效。

## 💾 五、数据迁移：五种存储之间自由搬

很多朋友是先用文件存储起步的，业务长大后再换数据库；也有人想从 MySQL 换到 PostgreSQL。v2.6.0 新增了**存储数据迁移**，作业、日志、系统设置、通知四类数据可以在五种存储之间直接搬，不用再手写脚本。

### 支持的存储与方向

| 存储类型 | 说明 |
| --- | --- |
| 文件 | 目录下的 JSON 文件，零依赖 |
| MySQL | 需安装 `Chet.QuartzNet.EFCore.MySQL` |
| PostgreSQL | 需安装 `Chet.QuartzNet.EFCore.PostgreSQL` |
| SQLite | 需安装 `Chet.QuartzNet.EFCore.SQLite` |
| SQL Server | 需安装 `Chet.QuartzNet.EFCore.SqlServer` |

五种存储**任意两两互转**（共 20 个方向），也支持文件 ↔ 数据库。同一存储类型之间不允许直接迁移（例如两个 SQLite 配置档互相搬），可以先导出到文件再导入。

### 迁移什么

- **作业数据**：作业定义、触发器、Cron、执行状态
- **作业日志**：执行历史记录
- **系统设置**：键值型配置
- **通知消息**：通知历史记录

未勾选时默认四类全选。服务端按「系统设置 → 作业数据 → 通知消息 → 作业日志」的顺序写入，避免作业先于设置落库导致行为不一致。

### 三种写入模式

| 模式 | 语义 | 适用场景 |
| --- | --- | --- |
| 合并 Merge | 不存在则插入，存在则跳过 | 增量同步，可重复执行 |
| 覆盖 Overwrite | 不存在则插入，存在则更新 | 以源为准刷新目标 |
| 替换 Replace | 先清空所选实体，再全量写入 | 整体搬迁、环境重建 |

合并模式天然幂等，对同一源反复迁移也不会产生重复数据。

### 预检、进度与校验

1. **迁移预检**：先算清楚源端 / 目标端各有几条数据、预计写入多少、跳过多少，确认无误再执行
2. **后台执行**：迁移跑在后台任务里，页面轮询进度，分阶段展示「参数校验 → 连通性探测 → 备份 → 目标建表 → 迁移 → 校验」
3. **自动备份与建表**：文件源自动备份；数据库目标自动执行 EF Core 迁移建表或升级结构
4. **迁移后校验**：数量校验 + 首 / 中 / 尾抽样校验，差异只告警不阻断，方便事后对账
5. **可暂停调度器**：迁移期间可临时把调度器置为 Standby，避免写入过程被任务执行干扰

每批默认处理 500 条，文件端的日志与通知采用流式读写，数据量大也不会把内存撑爆。

### 安全与收尾

- 数据库连接字符串只存在于服务端，前端拿不到
- 文件源路径必须在服务端允许列表内
- 迁移**不会自动修改存储配置**，完成后会给出建议的配置片段，按提示修改 `QuartzUI:StorageType`、`DatabaseProvider` 与连接字符串后重启即可

入口在系统配置页，整个流程不需要写一行代码。

## 📦 六、升级指南

### 1️⃣ 更新 NuGet 包

```bash
dotnet add package Chet.QuartzNet.UI --version 2.6.0
```

数据库存储模式请同步更新对应的 EFCore 扩展包：

```bash
dotnet add package Chet.QuartzNet.EFCore.MySql --version 2.6.0
dotnet add package Chet.QuartzNet.EFCore.PostgreSql --version 2.6.0
dotnet add package Chet.QuartzNet.EFCore.SqlServer --version 2.6.0
dotnet add package Chet.QuartzNet.EFCore.SQLite --version 2.6.0
```

### 2️⃣ 数据库迁移（数据库存储模式必做）

v2.6.0 新增了作业依赖字段，四个数据库提供程序均已生成 `AddJobDependencies` 迁移：

```bash
dotnet ef database update
```

> ⚠️ **注意**：如果只更新 `Chet.QuartzNet.UI` 而不更新 EFCore 扩展包，作业依赖字段会写入失败。

### 3️⃣ 文件存储模式

无需任何操作，程序启动后自动兼容旧数据文件，依赖字段默认为空。

## 🎉 总结

v2.6.0 的核心思路是：**不去做重，只把高频场景做顺。**

- 想串流程 → 配两个前置依赖就够了
- 想批量处理 → 选中小小一个勾，一次搞定
- 想省心 → 日志清理交给后台，配置一次长期有效
- 想换存储 → 五种存储任意互转，预检 + 校验不怕搬错

如果你的定时任务还停留在「手写 Cron + 看服务器日志」的阶段，不妨试试这个轻量方案。
