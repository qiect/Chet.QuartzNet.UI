# 🛡️ Chet.QuartzNet.UI v2.7.0 发布：进程崩了也能知道谁没跑完，中断补跑 + 排水停机 + 页面焕新！

从 v2.6.0 到 v2.7.0 一共 24 次提交、80 多个文件改动。这次没有继续加"业务功能"，而是补上了定时任务系统最容易被忽略、但运维最痛的一块：**可靠性**。

先看三个真实场景：

| 场景 | 以前 | v2.7.0 |
| --- | --- | --- |
| 发布重启，任务跑到一半 | 日志里什么都没有，不知道谁被砍了 | 自动标记「中断」，按策略补跑并提示 |
| 数据库连接抖了一下，作业失败 | 要自己翻日志猜 | 「仅看异常」一键筛出失败 + 中断 |
| 停机维护，想等任务跑完 | 只能硬停，或者干等 | 「排水」：不再接新触发，等执行完自动停 |

---

## 💥 一、先说问题：为什么以前"看不见中断"

Quartz.Net 默认用内存存储（`UseInMemoryStore`），进程一挂，触发器、运行态全部丢失；而执行日志是**执行结束后才写一条**。两件事叠加的结果是：

> 进程崩溃时，那些"跑到一半"的任务在后端**根本不存在任何记录**。

你既不知道是哪个作业被砍了，也不知道它跑了多久，更谈不上补跑。所以 v2.7.0 的改造顺序是：**先把日志的生命周期做实，再谈恢复。**

---

## 🫀 二、执行日志重构：开始即落库 + 心跳

### 1️⃣ 执行开始就写 `Running`

`JobToBeExecuted` 钩子在所有"可能阻止执行"的校验（暂停、依赖）都通过之后，才创建一条 `Running` 日志并写进数据库；`JobWasExecuted` 收尾时改成**更新同一条记录**，不再新增。

带来的直接变化：

- 页面上第一次能看到「运行中」的作业，耗时每秒递增；
- 进程被强杀时，这条 `Running` 记录还在，成了判定中断的唯一依据；
- `JobExecutionVetoed` 也会按 logId 收尾，避免「已建行却被否决」留下僵尸任务。

### 2️⃣ 心跳续期

新增 `JobHeartbeatHostedService`，按 `HeartbeatIntervalSeconds`（默认 15 秒）把本进程所有活跃执行批量续一次期：

- **只在有执行时写库**，空闲零开销；
- 文件存储一次写、数据库存储一条 `ExecuteUpdate`；
- 心跳失败只记 warn，不阻断作业。

### 3️⃣ 判定中断

一条日志被判为中断，条件很干脆：

```
Status == Running
且 (HeartbeatTime ?? StartTime) < now - LeaseDurationSeconds
且 条件更新成功（Status = Running → Interrupted）
```

`UPDATE ... WHERE LogId = @id AND Status = Running` 影响行数为 1 才算抢到；多实例同时启动时只有一方成功，另一方跳过。文件存储在同一把锁内做「读-判-写」，语义一致。

## ♻️ 三、启动补偿：可开关、可延迟、可跳过、可限次

判定出中断之后，启动流程会按策略决定补不补：

| # | 条件 | 结果 |
| --- | --- | --- |
| 1 | 未启用中断补偿 | 只标中断，不补跑 |
| 2 | 已达最大执行次数（默认 3） | 跳过，防"启动即崩"死循环 |
| 3 | 作业已删除 / 已禁用 | 跳过 |
| 4 | 作业关闭了自动重跑 | 跳过 |
| 5 | 距下次触发不足阈值（默认 120 秒） | 跳过，等下次正常跑 |
| 6 | 策略为「只标记不补偿」 | 跳过 |
| 7 | 策略为「每个作业补最近一次」且存在更新的中断 | 跳过 |
| 8 | 触发失败 | 记为失败并写原因 |

### 补偿是"整段重跑"，不是断点续传

这点必须说清楚：

- **不是断点续传**：从头再跑一遍，不是从中间继续；
- **不是 exactly-once**：语义是 at-least-once，**非幂等作业（转账、发消息、扣库存）请在作业上关闭自动重跑**；
- **不保证跨节点调度**：Quartz 仍是内存存储，多实例只共享作业定义与日志表，恢复靠日志行原子认领。

### 补偿链可以追溯

补偿产生的新日志是一条正常执行记录，`TriggerType = Recovery`，并通过 `RecoverySourceLogId` 指回被补偿的那条中断记录；源记录的 `CompensationLogId` 反向指向它。日志列表的「触发来源」列会显示「补偿重跑」，鼠标悬浮可以看到原执行时间与第几次执行。

即使补偿触发的瞬间进程又崩了，预建的 Running 行会被下一轮扫描按中断处理，attempt + 1 继续往下传，**账不会丢**。

### 手动重新执行

中断记录支持直接点「重新执行」：

- 只有中断行才会出现这个按钮；
- 提交前有确认，明确提示"将整段重跑，可能产生重复副作用"；
- 已补偿过的记录返回冲突（409），前端只提示并刷新，不弹系统错误。

## 🚰 四、排水与优雅停机

以前只有两种情况：**跑着** 或 **被硬停**。v2.7.0 补上第三种：**排水**。

| 操作 | 停止接收新触发 | 等待执行中任务 | 可恢复 |
| --- | --- | --- | --- |
| 停止调度器 | ✅ | ❌ 立即关闭 | 重新启动 |
| 排水 | ✅ | ✅ 等待 + 超时 | 排水未完成可「恢复调度」 |
| 应用关闭 | ✅ | 按停机策略 | 下次启动恢复 |

排水过程：

1. 调度器进入 `Standby`，不再接收新触发；
2. 后台每 500ms~1s 检查执行中任务数；
3. 归零 → 平滑 `Shutdown`，状态自动回落到「已停止」；
4. 超时 → 强制关闭，并把本进程还在执行的登记项标记为中断，交由下次启动补偿。

排水期间，作业页顶部会显示黄色徽标「排水 · 等待 N 个任务完成」，启动按钮置灰，手动触发会被拒绝并提示原因。

### 应用关闭钩子

新增 `GracefulShutdownHostedService`，在 Quartz 关闭之前执行停机策略：

| 停机模式 | 行为 |
| --- | --- |
| 立即停止 | 不等待，直接终止 |
| 排水后停止（默认） | 停止接收新触发，最多等 `DrainTimeoutSeconds`（默认 60 秒） |

> ⚠️ 宿主的 `HostOptions.ShutdownTimeout` 默认 30 秒，会先于自定义等待触发。若希望等待更久，需要同步调大宿主超时。强杀进程不会走这个钩子，但下次启动扫描的结果是一致的。

## ⚙️ 五、停机与恢复配置

系统配置页新增独立的「停机与恢复」分区，顶部会汇总「重启后生效 N 项」，点开可看到每一项的**旧值 → 新值**，避免"改了不知道有没有生效"。

| 分组 | 配置项 | 默认值 |
| --- | --- | --- |
| 停机 | 停机模式 | 排水后停止 |
| 停机 | 排水超时（秒） | 60 |
| 恢复 | 启用中断补偿 | 开启 |
| 恢复 | 补偿延迟（秒） | 30 |
| 恢复 | 心跳间隔（秒） | 15 |
| 恢复 | 租约时长（秒） | 60 |
| 恢复 | 临近触发跳过阈值（秒） | 120 |
| 恢复 | 补偿策略 | 每个作业补最近一次 |
| 恢复 | 最大执行次数 | 3 |
| 恢复 | 默认允许中断补跑 | 开启 |
| 恢复 | 中断日志保留（天） | 30 |

几个细节：

- 这些都是**启动期配置**，保存只落库，不改当前运行值；
- 服务端强校验「租约 ≥ 2 × 心跳」，不满足直接拒绝，不做静默纠正；
- 补偿策略选「全部补偿」时会二次确认，避免瞬时补跑风暴；
- 补偿关闭或策略为「只标记不补偿」时，下方不生效的参数会置灰并给出提示。

### 作业级三态开关

作业编辑对话框新增「中断后自动重跑」三态选择：

| 选项 | 含义 |
| --- | --- |
| 跟随全局（默认） | 由系统配置决定 |
| 开启 | 该作业一律补跑 |
| 关闭 | 该作业一律不补跑，优先级最高 |

作业列表的状态列后会显示一个小图标（⚡ / ⊘ / —），hover 即可看到三态含义，不用点进编辑页确认。

## 🔔 六、启动提示：这次崩了几个，补了几个

应用启动时，布局层会请求一次恢复汇总，如果有中断就弹出提示：

```text
本次启动检测到 2 个中断执行
已自动重跑 1 个，跳过 1 个，失败 0 个
```

- 按 `bootId` 去重，刷新页面不会重复弹，重启后再弹一次；
- 补偿还在进行中时最多再轮询 3 次，不无限等待；
- 「查看详情」直接跳日志页的异常筛选；
- 接口缺失或失败时静默跳过，不影响首屏。

## 🎨 七、界面同步焕新

### 1️⃣ 分析页：KPI 换成真正有用的四张卡

移除了与趋势图 / 健康象限重复的「执行活跃度」「耗时水位」，换成：

| 卡片 | 内容 |
| --- | --- |
| 作业总览 | 总数、启用 / 禁用 / 暂停 |
| 调度运行态 | 执行中线程与槽位占用、调度器状态、运行时长、待补偿数，5 秒轮询实时刷新（页面不可见时暂停） |
| 执行质量 | 成功率、失败数、日环比 |
| 风险巡检 | 沉默作业（启用但近 7 天无执行）、失败最多的作业 |

顺带修了两个老问题：执行趋势的统计口径（按天聚合而非按小时）、切换筛选时的请求竞态导致的错图。深色主题下的图表配色与热力图空格子也一并补齐。

### 2️⃣ 日志页：从"看记录"变成"处理记录"

- **状态新增「中断」**（洋红标识），与成功、失败、已跳过并列；
- **新增「触发来源」列**：定时 / 手动 / 补偿重跑，补偿可追溯到源记录；
- **「仅看异常」开关**：一键只看失败 + 中断，排查时不必反复切筛选；
- **操作列新增「重新执行」**：仅中断行可见，行级 loading；
- **详情弹窗补充恢复信息**：最后心跳、失联时长、补偿状态、跳过原因；
- **日志配置搬到这里**：保留天数、最大条数、清理间隔、当前日志总量，在日志页直接改，不用再跑系统配置页；
- **列设置持久化修复**：改完列宽 / 显示项，刷新后不再丢。

### 3️⃣ 通知页：模板选择卡片化，推送预览所见即所得

- 消息模板改为**卡片式选择器**（HTML / Markdown / TXT / JSON），下方实时预览；
- 新增 **JSON 结构化模板**：作业执行、调度器异常、测试通知都按所选模板输出，方便对接自动化；
- 模板预览从"点开看"改成**悬停浮层**，标题栏只保留推送预览入口，界面更干净。

JSON 模板输出示例：

```json
{
  "eventType": "jobExecution",
  "jobName": "order-sync",
  "jobGroup": "DEFAULT",
  "status": "failed",
  "statusText": "失败",
  "executionTime": "2026-11-14 10:00:00"
}
```

### 4️⃣ 系统配置页：分区切换 + 环境标识

- 顶部「停机与恢复 / 数据迁移」分区切换按钮放大，配置分组更清晰；
- 服务标识卡片强化环境标识（DEV / TEST / UAT / PROD）的视觉层级；
- 「重启后生效 N 项」可以点开看旧值 → 新值明细；
- 数据迁移的预检结果与迁移摘要统一改为弹窗，基础信息区更紧凑；仅配置一种存储时给出空状态提示。

## 🧰 八、稳定性与性能修复

这一版还修了不少"不显眼但很烦"的问题：

| 问题 | 处理 |
| --- | --- |
| 文件存储并发读写互相阻塞 | 读不加锁，写临时文件后原子替换，读改写收敛到单锁区间 |
| SQLite 下页面查询被作业写入卡住 | 连接启用 WAL 与 `busy_timeout` |
| 页面查询带变更跟踪、白占内存 | 分析页与列表查询统一 `AsNoTracking`，清空日志改用 `ExecuteDelete` |
| 配置 / 迁移把中文写成 Unicode 转义 | 统一 JSON 序列化选项，中文原样落库 |
| 作业类名与 API 地址切换类型时互相带值 | 拆成独立字段维护 |
| 列表搜索后表头排序标识丢失 | 统一 grid 排序标识组件 |
| 日志详情执行时长换行错位 | 调整列宽与样式 |
| 中断日志被误判、重试状态显示错误 | 修正状态机与重试判定 |
| 排水状态残留、停机策略不统一 | 状态机收敛，`Wait` 作为 `Drain` 的兼容别名 |

另外，CI 也顺手整理了：站点部署与 NuGet 发布拆成两个工作流，NuGet 发布改用 **Trusted Publishing (OIDC)**，不再依赖长期 API Key。

## 📦 九、升级指南

### 1️⃣ 更新包（版本号需一致）

```bash
dotnet add package Chet.QuartzNet.UI --version 2.7.0
```

数据库存储模式**必须**同步更新对应的 EFCore 扩展包：

```bash
dotnet add package Chet.QuartzNet.EFCore.MySql --version 2.7.0
dotnet add package Chet.QuartzNet.EFCore.PostgreSql --version 2.7.0
dotnet add package Chet.QuartzNet.EFCore.SqlServer --version 2.7.0
dotnet add package Chet.QuartzNet.EFCore.SQLite --version 2.7.0
```

> ⚠️ 四个 Provider 已经各带一个 `AddRecoveryAndDrainFields` 迁移。宿主升级了 UI 却没升级 Provider，写入新字段会直接失败。

### 2️⃣ 数据库结构

启动时会自动执行 `MigrateAsync`，新增内容：

| 表 | 变更 |
| --- | --- |
| `quartz_jobs` | `RerunOnRecovery`（可空 bool） |
| `quartz_job_logs` | 实例标识、启动标识、触发来源、补偿链、心跳、中断时间等 11 列 |
| 索引 | `(Status, HeartbeatTime)`、`(Status, CompensationStatus)`、`RecoverySourceLogId` |

全部新列可空或有默认值，老库可直接升级；老版本代码读新库会忽略多余列，**结构可回滚**（回滚后中断记录仍可见，只是旧版本不会补偿）。

生产环境建议先在备份库演练一次。

### 3️⃣ 文件存储

无需操作，旧 JSON 天然兼容缺省字段。

### 4️⃣ 升级后建议做的两件事

1. **梳理非幂等作业**，在作业上把「中断后自动重跑」设为关闭；
2. 检查宿主 `ShutdownTimeout` 是否大于「排水超时」，否则排水会被宿主提前打断。

## 🎉 总结

v2.7.0 的主线只有一句话：**让"出事"这件事变得可见、可控、可追溯。**

- 崩了 → 知道哪条执行被中断，带了多久的心跳；
- 想补 → 按策略自动补，或手动点一下，来源链路清晰；
- 停服 → 排水等收尾，超时也有交代；
- 排查 → 「仅看异常」把失败和中断一次捞出来。

如果你的定时任务已经跑在关键链路上，这一版值得升级。
